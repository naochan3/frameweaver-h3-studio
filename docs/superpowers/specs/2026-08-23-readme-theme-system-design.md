# README LP化・テーマシステム設計

## 1. 状態

- 設計承認: 2026-08-23（ユーザーの `Go`）
- 対象ブランチ: `feat/readme-theme-system`
- ベース: `origin/main` (`c65e8a4`)
- 実装状態: 未着手

## 2. 目的

GitHubのREADMEだけで、FrameWeaver H3 Studioの実画面、価値、必要環境、セットアップ順、検証方法を短時間で理解できる状態にする。同時に、既存のオレンジ系デザインを維持しながら、利用者がサイトのテーマカラーを安全に変更・保存できる小さなテーマ基盤を導入する。

## 3. 成功条件

1. GitHub上のREADME冒頭で、実際のデスクトップUIとスマホUIを高解像度で確認できる。
2. 新規利用者がREADMEの順序どおりに、依存導入、ComfyUI、モデル、Ollama、WebUI、Tailscale接続を設定できる。
3. 各セットアップ段階に、観測可能な合格条件と失敗時の確認先がある。
4. ヘッダーからテーマを変更でき、再読込後も選択が維持される。
5. 既定テーマは現行の見た目を保持し、既存の生成操作・レスポンシブ表示に回帰がない。
6. README画像を再生成する手順がリポジトリ内に残り、画像の寸法と参照切れを検証できる。

## 4. 非目標

- 今回は任意色を入力するカラーピッカーを実装しない。
- ダークモード全体の設計・実装は行わない。
- ComfyUI、Ollama、モデルのインストーラーは新規作成しない。
- Fleet/GPUルーティング、Discord認証、ジョブ基盤は変更しない。
- README用に実在しない生成結果や接続状態を合成しない。

## 5. 現状と課題

- `README.md` は情報量が多い一方、冒頭にUI画像、目次、最短経路、検証表がない。
- 色は `src/index.css` のTailwind v4テーマ変数へ固定値で定義されている。
- `cream`、`accent`、`ink` の意味的な色系列は既にあり、テーマ切替の土台として再利用できる。
- README画像、画像更新スクリプト、UIキャプチャ規約が存在しない。
- 現行 `main` の基準検証は `npm test` 86件成功、`npm run lint` 成功、`npm run build` 成功、`npm audit` 0件。
- 最新2コミットはプロンプト強化・翻訳・コピー処理の変更で、README、ヘッダー、色トークンとは競合しない。

## 6. 採用アプローチ

### 6.1 READMEをLP型の情報設計へ再編する

READMEは次の順序にする。

1. ヒーロー: 製品名、短い価値説明、主要バッジ、デスクトップUI
2. スマホ対応: モバイルUIとTailscale経由の利用イメージ
3. 主な機能: 動画、画像、プロンプト強化、履歴、LoRA、VRAM操作
4. 5分で理解する構成図: Browser → FrameWeaver → ComfyUI/Ollama → Models/Output
5. セットアップ: 前提 → clone/npm → ComfyUI → addon → models → Ollama → 起動 → Tailscale
6. 検証マトリクス: 段階、コマンドまたは操作、期待結果、ログ/確認先
7. モデルとディスク容量
8. 日常操作とトラブルシュート
9. 開発者向け: test/lint/build、スクリーンショット更新、リポジトリ構成

詳細なモデル一覧は残すが、冒頭の導線を阻害しない位置へ移す。現時点で自動検証できない性能値やセットアップ結果は、実測済みと一般的目安を区別する。

### 6.2 テーマはプリセット方式にする

テーマIDは固定の文字列unionとして管理し、初期実装は次の3種類とする。

- `ember`: 現行互換のオレンジ/クリーム（既定）
- `ocean`: シアン/青系
- `violet`: 紫系

テーマごとに `cream-*`、`accent-*`、`ink-*` のCSS変数を上書きし、既存Tailwindクラスを再利用する。Reactコンポーネントへ色値を直接埋め込まない。

### 6.3 テーマ状態の責務

- `src/lib/theme.ts`: Theme ID、表示名、検証、読み込み、保存、DOM反映
- `src/components/ThemePicker.tsx`: アクセシブルなテーマ選択UI
- `document.documentElement.dataset.theme`: CSSテーマの唯一の反映先
- `localStorage` の `frameweaver-theme`: 端末内の永続化先
- 不明または壊れた保存値: `ember` へフォールバック

テーマは生成ストアへ混ぜない。生成状態と外観設定のライフサイクルが異なるためである。初回描画前に保存値を反映し、可能な範囲で色の瞬間的な切替を防ぐ。

### 6.4 UI配置

テーマ選択はヘッダー操作群へ置く。スマホでは横幅を圧迫しないコンパクトな選択UIとし、表示名または `aria-label` で目的を明示する。テーマ追加でヘッダー全体が横スクロールしないことを合格条件にする。

### 6.5 README画像

- 保存先: `docs/assets/readme/`
- デスクトップ: 2560×1440 PNG（GitHub表示幅はHTML属性で制御）
- スマホ: 1170×2532 PNG相当の高密度キャプチャ
- 対象: 実装した実UI。認証情報、端末名、個人履歴、ローカル/Tailscale固有URLは写さない。
- READMEには相対パスで埋め込み、GitHub上で直接表示できるようにする。

画像更新は `docs/README-SCREENSHOTS.md` に、固定viewport、固定テーマ、ガイド表示状態、保存先を記録する。今回は新しいブラウザ自動化依存を追加せず、既存のブラウザ環境で実画面を撮影する。バックエンドに依存する表示は公開して問題のない実状態だけを使い、実在しない接続状態や生成結果を作らない。

## 7. 検証設計

### 7.1 自動検証

| 対象 | 検証 |
|---|---|
| テーマ定義 | 3テーマが一意で、既定値が `ember` |
| 保存値 | 正常値の復元、不正値のフォールバック |
| DOM反映 | `data-theme` が選択に追従 |
| UI | 既存ブラウザでテーマ選択、再読込、PC/スマホ幅を確認 |
| 品質 | `npm test` |
| 静的検査 | `npm run lint` |
| 本番成果物 | `npm run build` |
| README資産 | Node標準機能だけの小さなスクリプトで参照ファイル存在とPNG寸法を確認 |

### 7.2 画面検証

1. デスクトップ幅で3テーマを切り替え、主要面のコントラストと選択状態を確認する。
2. 390px相当でヘッダー、入力、生成ボタンに横スクロールや重なりがないことを確認する。
3. 再読込後にテーマが維持されることを確認する。
4. README用PNGを原寸表示し、文字が判読可能でぼけ・切れ・秘密情報がないことを確認する。
5. GitHub Markdown相当で画像パスと見出しリンクを確認する。

### 7.3 セットアップ検証表の表現

各段階を「操作」「期待結果」「失敗時の確認」の3点セットにする。例:

| 段階 | 操作 | 期待結果 | 失敗時 |
|---|---|---|---|
| WebUI依存 | `npm ci` | exit 0、脆弱性結果表示 | Node/npmバージョンとlockfile |
| 単体テスト | `npm test` | 全テスト成功 | 失敗suiteと最初のerror |
| ComfyUI | `/system_stats` 等のread-only確認 | HTTP 200、GPU情報 | listen port、ログ、CORS/proxy |
| Ollama | 制限付きgatewayのmodels確認 | 対象モデルが列挙 | Ollama起動、モデル名 |
| UI | ブラウザでアクセス | 接続状態と入力UI表示 | FrameWeaver API、ComfyUI |
| Tailscale | tailnet URLへアクセス | 認証後にUI表示 | DNS、Serve、ACL |

実際のエンドポイント名は実装時に現行コードと起動構成を再確認して確定する。

## 8. エラー処理

- 保存テーマが壊れていても起動を妨げず、既定テーマを使う。
- `localStorage` が利用不能でもメモリ上の切替は動作させる。
- README資産検証時に画像欠落または寸法違反があれば非ゼロ終了する。
- README検証は不足サービスを成功扱いにせず、未検証項目として明示する。

## 9. アクセシビリティと性能

- テーマ選択はキーボード操作可能で、可視ラベルまたはアクセシブル名を持つ。
- 色だけで接続・エラー・選択状態を伝えない。
- 各テーマで主要テキストと背景のコントラストを目視および可能な範囲で自動確認する。
- テーマ切替は追加ネットワーク要求を発生させない。
- CSS変数の上書きを利用し、テーマごとのCSSバンドル複製を避ける。

## 10. 変更予定範囲

- `README.md`
- `src/index.css`
- `src/main.tsx` または初期テーマ適用箇所
- `src/lib/theme.ts` と最小テスト
- `src/components/ThemePicker.tsx`
- `src/components/Header.tsx`
- `docs/assets/readme/*`
- `docs/README-SCREENSHOTS.md`
- Node標準機能だけのREADME資産検証スクリプト
- `package.json`（検証コマンド追加のみ。新規依存なし）

対象外の生成ロジック、ComfyUI workflow、Ollama prompt、認証、GPUルーティングは変更しない。

## 11. ロールバック

テーマ機能はCSS変数上書き、選択コンポーネント、初期化処理に閉じる。問題時はテーマ選択UIと `data-theme` 上書きを外せば、`ember` の既定値だけで現行外観へ戻せる。README画像と文書は実行時挙動から独立している。

## 12. Ponytailレビューによる削減

- `yagni`: 新規Playwright依存とE2E基盤。既存ブラウザで実画面確認し、必要性が反復運用で証明された時だけ追加する。
- `native`: テーマ用のReact Context/Zustand store。`data-theme`、CSS変数、`localStorage` で置き換える。
- `delete`: 任意色、ダークモード、テーマ拡張API。今回必要な3プリセットだけを定義する。
- `shrink`: README検証フレームワーク。Nodeの `fs` とPNGヘッダー確認だけの単一スクリプトにする。

net: 新規依存0、状態管理層0、E2E設定一式を回避。

## 13. 実装前の残確認

設計レビュー後の実装計画では、READMEに記載する現行の正式ポート、Tailscale Serve経路、ComfyUI read-only確認APIをコードと運用状態から再確認して確定する。
